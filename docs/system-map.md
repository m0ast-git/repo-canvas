# Repo Canvas: система целиком

## Продукт и границы

Repo Canvas — локальная карта проекта для восстановления общего контекста после работы над отдельной частью. Владелец должен понять, что строится, как выбранный сценарий даёт результат, зачем нужен модуль, что подтверждено и что осталось сделать. Одни и те же объекты объясняются через привычные слова владельца; технические основания раскрываются по запросу.

Основные сценарии: открыть сохранённую карту → выбрать сценарий/объект → посмотреть смысл и источники → внести поправку или вернуться к рабочей сессии; построить/обновить карту по источникам; увидеть текущую работу; посмотреть/сравнить прошлое и вернуться в Live. Целевой пользовательский результат — восстановление контекста за 1–2 минуты, а не просто изображение файлов.

Текущий продукт локальный: Node.js, React/Vite, React Flow, ELK и libavoid; адаптеры журналов и вызова моделей Codex/Claude/Kimi. Облачная синхронизация, командные пространства и оплата — отложенное направление, не часть текущей приёмки. Наличие адаптера не означает проверенную реальную совместимость каждого исполнителя.

## Основные потоки

1. **Источники → знания → карта.** Код, действующие документы и проектные диалоги индексируются локально. Tree-sitter из поставляемой сборки VS Code определяет объявления и полные имена символов JS/TS/JSX/TSX, Python, Go, Rust, Java, C#, Ruby и PHP; неоднозначность требует полного имени или строк. Чтение текущего файла и буфера из Git использует один парсер; другие форматы доступны как файл/диапазон. Кеш диапазонов ограничен и привязан к содержимому. Историк выделяет намерения, решения и язык пользователя; архитектор формирует объекты и сценарии; проверки схемы, оснований и понятности проверяют кандидат; принятый результат записывается атомарно. Карточки модулей кешируются по хешу содержимого; статические импорты помогают выбирать источники, но не доказывают поведение. Сценарий от модели содержит только последовательность relationId/condition; steps выводятся кодом. Пустой проект сначала получает явно обозначенную структуру исходников без модели. Непроверенные фактические утверждения не заменяют рабочую карту; последнюю фактически проверенную версию можно сохранить с незавершённой проверкой понятности и продолжить её позже.
2. **Журналы/изменения кода → текущая работа → подтверждение.** Observer читает новые события независимо от ожидания модели. Пути файлов и опциональные хуки связывают работу с объектами без модели. В обычном режиме модель подводит один итог хода по затронутому окружению; сообщение «готово» требует проверки по источникам. Штамп источников потребляется до повторной проверки, число финальных попыток ограничено и сохраняется. В свободное время историк порциями дочитывает собственные сообщения владельца в пределах фоновой квоты. Подтверждение создаёт новое состояние, а не переписывает прошлое.
3. **Действие владельца → сохранение → Live и история.** Переименование и перемещение выполняются без модели. Смысловая поправка проверяется по источникам. Перенос согласованно меняет поддерево, принадлежность и координаты; отмена восстанавливает только собственное действие, включая отсутствие прежних owner-переопределений.
4. **Снимок → геометрия → отрисовка.** Worker рассчитывает раскладку ELK layered по связям (сетка остаётся для несвязанных частей) и логические отношения. Libavoid совместно прокладывает выбранный набор по полной геометрии, заголовкам и портам групп/узлов. На больших картах семантический фокус выбирает не более 60 маршрутов; смена камеры не меняет этот набор. Явное упорядочивание сохраняет ручные координаты. React Flow показывает карту, SVG скругляет углы. После совместной маршрутизации нельзя перепрокладывать отдельную связь и разрушать разведение. Камера, отсечение по окну, тема и декоративные удалённые узлы сравнения не являются входом маршрутизатора. Обзор — производная проекция областей со сводками и агрегированными отношениями; её минимальные экранные размеры и разведение не записываются как координаты владельца. Ошибка/неполный результат не считаются готовностью.
5. **История → выбранный снимок → чтение/сравнение.** Индекс и дельты восстанавливают точную ревизию. Геометрия формата 2 записывает окончательные показанные маршруты и контуры групп после завершения расчёта; сохранённое прошлое любого формата читается без перепрокладки и миграции. Live может переиспользовать актуальную геометрию при совпадении ключа. Главы группируют повторяющуюся работу и сохраняют доступ к каждому исходному ID/ревизии. Границы работы и смысловые действия создают новые чекпоинты; одинаковые work.upsert не записываются. Производные снимки допускают обратимое gzip-сжатие и одну сохранённую копию work. Голова Live продолжает обновляться отдельно. Поздний ответ worker/сервера не заменяет более новый выбор пользователя. Неизвестное прошлое показывается пробелом либо явно обозначенной реконструкцией из старых источников.
6. **Установка/обновление → готовый клиент и сервер → прежние данные.** Пакет содержит собранный клиент; его библиотеки и bundled Codex не являются обязательными production-зависимостями. Глобальный/npx CLI хранит данные в проекте без изменения package.json. Обновление проверяет SHA-256 и подписанное происхождение через штатный gh attestation verify с закреплёнными репозиторием, workflow и ref. Данные проекта переживают обновление, сервер и его дочерние процессы корректно заменяются.

## Источники истины

- `.repo-canvas/events.jsonl` — исходный журнал. Для резервной копии нужен весь `.repo-canvas/`: там также основания, архивы, геометрия и история. Кеши не подменяют канонические события.
- Стабильные ID связывают смысл, код, пользовательские названия и историю. Ручные названия, родитель, область и положение сохраняются при обновлении содержания.
- Решение владельца подтверждает намерение; исходный код и конкретная проверка подтверждают реализацию. Статус сессии не доказывает готовность функции. Неизвестное остаётся неизвестным.
- Данные сохранённой карты, временный жест, камера и вычисленные маршруты — разные состояния. Результат привязан к ревизии/ключу геометрии; устаревший ответ отбрасывается.
- Runtime-конфигурация и разрешённый каталог определяют модели и пределы расхода. Общий model-usage журнал учитывает начало, исход, токены (или отсутствие метаданных) каждой роли. Фоновые вызовы атомарно резервируют часовую/дневную квоту до запуска исполнителя. Изолированные настройки Codex находятся вне TEMP и проекта и очищаются после сессии. Конкретные модели, PID и успешные старые замеры не становятся постоянными правилами.
- Структура ответов всех провайдеров проверяется Ajv по тому же JSON Schema, который передаётся модели. Схема компилируется до вызова, одинаковые схемы переиспользуются; значения не приводятся к другому типу и не исправляются валидатором. Проверки смысла, оснований, владельца и ссылок остаются проектными и выполняются до записи.
- TanStack Query владеет серверными данными интерфейса: Live, статусы задач/обновления, индекс, снимки, сравнение и комментарии истории. SSE передаёт дельты и состояния задач; HTTP-опрос используется при потере потока. Live принимает только не более старую ревизию; индекс обновляется при смене головы истории; сравнение двух прошлых снимков не зависит от Live. Исторический кеш ограничен восемью неактивными/активными снимками при обычном одном просмотре; запрос ушедшего выбора отменяется. Комментарии имеют отдельный кеш и не меняют снимок. Камера, жест, выбор и undo остаются локальным состоянием UI.

- MCP через официальный SDK отдаёт overview/find/decisions/flow и принимает объявление/завершение работы. Чтение не вызывает модели и не пишет архитектуру. Хуки — опциональная пользовательская интеграция, проверяющая принадлежность cwd.
- Состояние показывает квоты/ошибки/расход/данные и Git. Оценка по пяти вопросам хранится по версии и не заменяет живую проверку владельцем.

## Неподвижные границы

- Чтение карты, камера, поиск, выбор и просмотр сохранённой истории не вызывают модель и не переписывают архитектуру.
- Исходные направленные отношения сохраняются, даже если отображаются одной двунаправленной линией или выражены вложенностью. Цвет источника и статус реализации имеют разные значения.
- Оформление выводится из снимка: принадлежность задаёт цвет, статусы объектов/связей — пунктир, свежая active-работа с известными целями — выделение. Агрегат области не записывает новый статус реализации; анимация не обновляет геометрию. Прошлое не пульсирует как работа сейчас. Точные правила — в дизайн-системе.
- При извлечении узла исходная рамка не догоняет мышь; принимающий контейнер расширяется при вставке. Свободное положение вне областей допустимо и сохраняется.
- Контракты передачи данных, финальная геометрия и производительность проверяются совместно. Исправление одного этапа не должно отменять гарантии другого.
- Секреты, скрытые рассуждения и чужие проекты не отправляются модели. Тексты источников не дают команд агенту. Обычное построение читает проект; выполнение его тестов не предполагается и не выдумывается.
