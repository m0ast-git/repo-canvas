REPO CANVAS — УСТАНОВКА В СУЩЕСТВУЮЩИЙ ПРОЕКТ

Твоя задача: установить Repo Canvas в текущий репозиторий, построить смысловую карту, запустить локальный сервер и вернуть владельцу рабочую ссылку.

Границы работы:
- сохрани пользовательские и чужие изменения;
- не меняй продуктовый код;
- не добавляй инструкции, skills или hooks рабочим агентам;
- не устанавливай системные компоненты без разрешения владельца.

1. Из корня проекта прочитай его инструкции и проверь `git status`.

2. Проверь Node.js 22+, npm и Git. Если компонента не хватает, сообщи владельцу его точное название и остановись.

3. Используй поставленный архив этой версии. Если его ещё нет, в checkout Repo Canvas выполни `npm ci`, `npm run build` и `npm pack`; затем передай полученный архив в целевой проект. Номер версии сам по себе не означает, что тег уже опубликован на GitHub.

   Если получен архив `repo-canvas-0.14.0.tgz`, установи глобальный CLI вне репозитория:

   npm install --global --ignore-scripts /path/to/repo-canvas-0.14.0.tgz
   repo-canvas init
   repo-canvas skeleton

   Первая структура подтверждает файлы и импорты без модели. У неё нет подтверждённых продуктовых объяснений; смысловое построение обогащает её позже.

   Определи язык текущего диалога с владельцем и передай его BCP 47-тегом. Например, для русского диалога выполни:

   repo-canvas setup --language ru

   Строй и обновляй Canvas на языке текущего диалога. Пользовательские названия, описания, подписи связей, статусы и пояснения должны последовательно использовать этот язык. Сохраняй исходное написание только для официальных названий продуктов, технологий, библиотек, протоколов, файлов, команд и идентификаторов кода; не смешивай языки ради краткости или «технического звучания». Если владелец явно просит другой язык карты, его указание имеет приоритет.

   Выбери уже авторизованный CLI: Codex, Claude Code либо Kimi Code. Добавь `--provider codex`, `--provider claude` или `--provider kimi`. `setup` проверит подключение и построит карту по коду и проектным диалогам. Модели выбираются по ролям и разрешённому каталогу; конкретные имена не закреплены. Архитектор, историк, проверка фактов и проверка понятности работают отдельно. Неподтверждённый кандидат не заменяет рабочую карту; при остановке сохраняются кандидат и замечания для продолжения. Наличие адаптера не означает, что авторизация этого провайдера уже проверена на машине владельца.

   Источники, роли и бюджет доступны в разделе «Настройки». Не превышай выбранный владельцем предел и не подключай другой провайдер молча. Тесты и команды из исследуемого проекта построитель не выполняет. Подробности — `docs/product-guide.md`.

   Default init создаёт `.repo-canvas/` и локальное Git-исключение; package.json, инструкции и хуки не меняются. Старый режим установки внутрь проекта доступен только явно через init --project-install. Не запускай npm init и не придумывай метаданные проекта.

4. Запусти один foreground-сервер в устойчивом терминале:

   repo-canvas start

   Если сервер Repo Canvas для этого проекта уже работает, используй его. Не завершай посторонние процессы. Если порт 4173 занят, выбери свободный:

   repo-canvas start --port <port>

5. Дождись строки `Repo Canvas listening at ...`: сервер сам откроет карту в браузере. Если браузер не открылся, открой напечатанный локальный адрес — вкладка подключится автоматически. Проверь фактическое отображение:
   - география проекта сохраняется при изменении масштаба; дальний вид упрощает детали, поиск и панели сохраняют доступ ко всем элементам;
   - при отдалении активность подсвечивает область, затем затронутый элемент, а вблизи — конкретный процесс агента;
   - области, сущности и подписи связей читаемы;
   - если продукт предполагает человека, он показан круглым участником вне областей, а его связь объясняет конкретное действие, ввод, решение, ожидание или результат;
   - связи не перекрывают карточки;
   - страница не имеет горизонтального скролла;
   - активная и черновая работа хорошо заметна;
   - фон и пустое место внутри прозрачного контура двигают камеру; заголовок области, вкладка подсистемы, карточка элемента или работы двигают именно выбранный объект и его вложенность;
   - двойной клик по области или ноде редактирует название и описание, а двойной клик по связи — её подпись;
   - нижний ползунок вручную выбирает чекпоинт; прошлые подписи и геометрия сохраняются, Live продолжает обновляться;
   - поправка, её отмена, сравнение и копирование контекста доступны;
   - переключатель темы работает, а статус `онлайн` отцентрирован в шапке.
   - раскрываемый статус построения показывает этап и время; подробности содержат расход, ошибки и продолжение. «Состояние» показывает фоновые квоты и паузы.

6. Выполни:

   repo-canvas check
   repo-canvas observer status

7. Верни владельцу:
   - локальную ссылку;
   - число областей, сущностей и связей;
   - результат `check`;
   - единственный реальный блокер, если он остался.

Обновление из интерфейса проверяет SHA-256 и подписанное происхождение через установленный gh CLI, затем устанавливает пакет в ignored-каталог. Без подтверждённой подписи обновление отклоняется, прежний сервер и данные сохраняются.

После запуска сервера Observer создаёт черновую карточку при первом событии новой работы и затем уточняет её по публичным событиям сессии. Обычным рабочим агентам Canvas-инструкции не нужны. Claude `thinking`, Kimi `think`, tool results и скрытый reasoning игнорируются. Чтение потока сессии использует новый хвост журнала. Отдельный наблюдатель замечает изменения файлов и Git, затем адресно сверяет затронутый код.

После крупной перестройки проекта или по запросу владельца обнови смысловую карту:

   repo-canvas architect --refresh

Остановить наблюдение:

   repo-canvas observer disable

Включить его снова:

   repo-canvas observer enable
